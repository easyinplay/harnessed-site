Это руководство вручную проводит вас по ритму из 5 стадий на реалистичном примере: **«Добавить rate limiter в наш Express API — 100 запросов в минуту на IP, на Redis.»**

Первый запуск `/auto` проходит все пять стадий от начала до конца:

```mermaid
flowchart LR
  D["① Discuss"] --> P["② Plan"] --> T["③ Task"] --> V["④ Verify"] --> S["⑤ Ship"]
  V -. "fail / gap" .-> T
```

## Стадия 1 — Discuss

```
/discuss "добавить rate limiter в наш Express API — 100 запросов в минуту на IP, на Redis"
```

`/discuss` параллельно оценивает три gate прояснения и запускает только сработавшие:

- **Стратегический gate** (`discuss-strategic`): это новая функциональность или изменение существующей инфраструктуры? Влияет ли на позиционирование продукта? Для rate limiter этот gate обычно запускает быструю проверку governance.
- **Gate фазы** (`discuss-phase`): есть ли ≥2 нерешённых вопроса по реализации? (Redis или in-memory? По маршрутам или глобально?) Этот gate проясняет и сохраняет находки в `findings.md`.
- **Gate подзадачи** (`discuss-subtask`): есть ли подзадачи с ≥2 принципиально разными подходами? Дизайн ключевого алгоритма проходит короткий brainstorming.

**Результат**: `findings.md` и `knowledge.md` в `.planning/PHASE-N/`.

## Стадия 2 — Plan

```
/plan "функциональность rate limiter"
```

`/plan` выполняет два шага по порядку:

1. **Ревью архитектуры** (условно) — если функциональность пересекает границы модулей или затрагивает новую инфраструктуру, параноидальный staff engineer из gstack проверяет дизайн
2. **План фазы** — GSD сохраняет `task_plan.md` с точными путями к файлам, критериями приёмки и порядком зависимостей

**Результат**: `.planning/PHASE-N/PLAN.md` и `task_plan.md`.

## Стадия 3 — Task

```
/task "реализовать middleware rate limiter"
```

`/task` выполняет 4 подшага на каждую подзадачу последовательно:

1. **Прояснить** — проверить спецификацию до написания кода, вскрыть неоднозначности
2. **Написать** — по принципам karpathy (минимальное жизнеспособное изменение, точечные правки)
3. **Протестировать** — TDD в основной логике: red → green → refactor
4. **Сдать** — gate `harnessed checkpoint complete` не пропускает дальше без дословного `COMPLETE`

## Стадия 4 — Verify

```
/verify "функциональность rate limiter"
```

`/verify` раздаёт до 7 подпроверок в зависимости от того, что изменилось:

| Проверка             | Когда срабатывает                              |
| -------------------- | ---------------------------------------------- |
| `verify-progress`    | всегда (приёмка UAT + синхронизация состояния) |
| `verify-code-review` | всегда (параллельный multi-agent fan-out)      |
| `verify-paranoid`    | критичный модуль или перед PR                  |
| `verify-qa`          | есть изменения UI                              |
| `verify-security`    | затронуты аутентификация или секреты           |
| `verify-design`      | есть изменения дизайна                         |
| `verify-simplify`    | всегда последней (убирает избыточную логику)   |

## Артефакты, сохраняемые в `.planning/`

```
.planning/
├── STATE.md          # источник истины по текущей фазе / прогрессу
├── ROADMAP.md        # карта маршрута фаз
└── PHASE-1/
    ├── PLAN.md       # список задач, пути к файлам, критерии приёмки
    ├── findings.md   # выводы стадии discuss
    ├── task_plan.md  # разбиение по подзадачам
    └── PROGRESS.md   # отслеживание прогресса в реальном времени
```

## Дальше

После завершения Verify запустите `/retro`, чтобы закрыть веху и зафиксировать выводы. Если бы вы запустили `/auto`, эти стадии сцепились бы автоматически — путь в одну команду описан в [Быстром старте](/ru/docs/getting-started/quickstart/).

Об архитектуре за каждой стадией читайте в [Ритме из 5 стадий](/ru/docs/concepts/five-stage-cadence/).
