## 原則

harnessed の要件 R8.1 はこう定めています。プロジェクト自身の開発サイクルは、自分のワークフローを使わなければならない。harnessed で出荷されるすべての機能は、harnessed がユーザーに公開しているのと同じ `/discuss`、`/plan`、`/task`、`/verify` のリズムで作られています。

これは努力目標ではなく、硬いゲートです。harnessed が自分自身を出荷するのに使えないワークフローは、動いていないワークフローです。

## 実際に何を捕まえたか

Phase 3.5 W2.1 Cycle 4 の期間中、チームは新しいオーケストレーション機能を実装するために harnessed リポジトリ自体に対して `/auto` を走らせていました。そこで `masterOrchestrator` の spawn 順序ロジックにバグが表面化しました。サブワークフローの初期化順序が狂い、plan 段階が `task_plan.md` を書き出す前に task 段階が始まってしまったのです。

このバグは dogfood 回帰として捕まりました —— ユニットテストには現れませんでした。その統合パスは、実際の `/auto` 実行が agent を spawn したときにしか通らないからです。harnessed が自分自身を使っていたからこそ、失敗は即座かつ明確でした。

この修正は P0 に格上げされました。信頼の契約に違反していたからです。harnessed が自分の開発をオーケストレーションできないなら、ユーザーが自分の開発を任せられるはずがありません。

## 実務上の含意

**Schema 変更は自己検証される。** harnessed がマニフェスト schema に新しいフィールドを追加すると、次の開発サイクルが harnessed 自身のマニフェストをそれで検証します —— `harnessed install` で自動的に、そして CI では `scripts/check-workflow-schema.mjs` で。schema の回帰はユーザーに届く前に dogfood 実行で現れます。

**新しいワークフローはまずストレステストされる。** どのワークフローも出荷前に harnessed リポジトリ自体で走らされます。そのワークフローを定義しているコードベースが、そのままテスト台になります。

**Dogfood のバグは P0。** harnessed 上で harnessed を走らせて壊れるなら、それは記録すべき既知の制限ではなく P0 インシデントです。これはツールをユニットテスト通過だけでなく端から端まで動く状態に保つ、強い動機になります。

## ユーザーにとっての意味

あなたが自分のプロジェクトで `/auto` を実行するとき、走っているのは harnessed 自体を出荷しているのと同じパイプラインです。dogfooding の継続的な圧力は次を意味します：

- 回帰はユーザー報告ではなく開発中に表面化する
- マルチ agent 協調のエッジケースが harnessed のリリースごとに実際に踏まれる
- 5 段階のリズムが、現実の、活発に保守されているコードベースで実戦検証されている

このメソドロジーは harnessed リポジトリの [docs/WORKFLOW.md](https://github.com/easyinplay/harnessed/blob/main/docs/WORKFLOW.md) に記載されています。
